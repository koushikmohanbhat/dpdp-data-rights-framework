# Security and production hardening

This page describes the security controls in the framework, what you must configure for
production, and what remains your responsibility.

Set `environment: production` in the config. The framework then **refuses to start** with
development-only settings (see [Production guardrails](#production-guardrails)). Run
`dpdp-rights -c <config> check-config` in CI to catch these issues before deploy.

## Threat model in brief

| Threat | Control |
|---|---|
| Raw personal data leaks into logs, traces, prompts, vectors, caches | Tokenisation at the edge; tokenising log filter; tokenising span exporter; masking when no principal is known; verification scans for raw values |
| Someone files an erasure or withdrawal for another person | Requester identity is verified upstream by the deployer; the API is authenticated, principals can only act on their own data, and `verified_by` / `verification_ref` are recorded on every request and certificate |
| Unauthorised API use | API keys (hashed) and OIDC JWTs, role checks on every endpoint |
| Insider reads sealed (legal-hold / escrow) data | Separate sealed KEK that only a break-glass role can decrypt; two-person grants; time-boxed; every attempt audited |
| Erasure silently fails halfway | Durable job queue with leases and retries; runs resume without repeating work; failures recorded in the certificate |
| Evidence is altered after the fact | Certificates hash-chained, signed with KMS asymmetric keys, archived to S3 Object Lock / GCS locked buckets |
| One tenant sees another tenant's data | Silo model: each tenant has its own database, vault and keys; tenant taken from the credential only |
| Unwrapped keys linger in memory | DEK cache TTL (default 300 s); sealed keys never cached |
| Vulnerable dependencies / tampered releases | Dependabot, CodeQL, a dependency audit gate that blocks releases at an agreed severity ([below](#dependency-audit-gate)), workflow actions pinned to commit SHAs, per-profile SBOMs checked against the audited pins, and build provenance attestation on release |

## Controls in detail

### Encryption and key management

**Envelope encryption, not a KMS key per person.** There is one key-encryption key (KEK) in KMS per
deployment (one per tenant with tenant silos), plus the separate sealed KEK below. Each Data Principal
gets an AES-256-GCM data key (DEK), generated by the framework, wrapped by the KEK and stored as one row
in the vault database (DynamoDB, Firestore or SQL). So a B2C deployment with ten million people still has
two KMS keys, and no per-key fees or key quotas grow with the user base.

**KMS calls:**

| Event | KMS calls |
|---|---|
| First data for a new person | 1 `Encrypt` (wrap the new DEK) |
| Any use while the DEK is cached (`vault.cache_ttl_seconds`, default 300; `cache_max_entries`, default 10,000 per process) | 0 |
| First use per process after the cache expires | 1 `Decrypt` |
| Erasure (`shred`): delete the wrapped-DEK row, values and lookups | 0 |
| Sealed hold or escrow: wrap / break-glass read | 1 `Encrypt` / 1 `Decrypt` each time (never cached) |

So the steady load is about (new people + people active in each 5-minute window, per process) calls,
not one per message. Size the KMS request quota for your peak and region from that, and raise the cache
size if active people per process exceed it. KMS prices and quotas change: take them from the provider's
page when sizing.

**Crypto-shredding** is deleting the wrapped-DEK row. Every token in logs, traces, vectors and backups of
other stores becomes unreadable at that moment. **The vault's own backups are the exception:** a restored
backup or point-in-time copy of the vault table brings the wrapped DEK back, and the KEK can still unwrap
it. Erasure is final when the vault's backup window has passed:
- AWS Terraform: DynamoDB point-in-time recovery, `vault_pitr_days` (default 35, 1-35).
- GCP Terraform: Firestore point-in-time recovery is not enabled; any scheduled backups you add set the window.
- SQL vault: the database's backup retention (the AWS RDS default in Terraform is 7 days).

Restrict restore permissions on the vault tables to the break-glass role, and state the window in the
published erasure period. Deleting a KEK is not erasure of one person: it erases everyone.

- DEKs are bound to their principal: KMS encryption context (AWS) or AAD (Google Cloud) = principal id.
- Values are encrypted with the token as associated data; tokens are `HMAC(DEK, type|value)`.
- **Sealed keys** (`hold_*`, `escrow_*`) are wrapped by a *separate* KEK
  (`vault.sealed_key_wrapper`). The application role may only `Encrypt` with it; `Decrypt` is
  reserved for the break-glass role (`deploy/terraform/*/security.tf`). On AWS the framework
  assumes `vault.sealed_role_arn` only for sealed unwraps.
- Keep the vault in a separate AWS account / GCP project from the lineage database and apps.

### Authentication and authorization (Rights API)
- `api.auth.mode`: `api_key`, `oidc` or `both`. `none` is rejected in production; in development every caller is an
  anonymous admin, and the `X-Dev-User` header only names that caller (so local walkthroughs can show separation of duties).
- API keys are stored as SHA-256 digests (`dpdp-rights hash-api-key <key>`), compared in constant time.
- OIDC: any issuer with a JWKS endpoint (Cognito, Google Identity Platform, Entra ID, Okta,
  Auth0, Keycloak). `iss`, `aud`, `exp`, `iat`, `sub` are required and verified.
- Roles: `principal` (self-service, own data only), `service`, `dpo`, `approver`, `reviewer` (case sign-off), `admin`.

| Endpoint | Roles |
|---|---|
| `POST /v1/consents` | service, dpo |
| `POST /v1/withdrawals`, `POST /v1/erasure-requests` | principal (own), service, dpo |
| `GET /v1/erasure-requests/{id}` and `/certificate` | owner principal, service, dpo |
| `GET .../certificate/verify`, `/v1/principals/{id}/lineage`, `/v1/sla` | dpo |
| `POST /v1/break-glass/grants`, `.../read` | dpo |
| `POST /v1/break-glass/grants/{id}/approve` | approver |
| `GET /v1/erasure-requests/{id}/case`, `.../evidence`, `GET /v1/audit-pack` | dpo, reviewer |
| `POST /v1/erasure-requests/{id}/manual-actions` | dpo, service |
| `GET /v1/rights/notice` | public (the Rule 14(1) notice) |
| `POST /v1/rights-requests` | principal (own), service, dpo; `on_behalf_of` (nominee) only service, dpo |
| `GET /v1/rights-requests/{id}` | owner principal, service, reviewer, dpo |
| `GET /v1/rights-requests`, `POST .../decision` | reviewer, dpo (never the case's submitter) |
| `POST /v1/rights-requests/{id}/response` (grievances) | dpo (never the person who raised it) |
| `GET /v1/rights-requests/{id}/access-report` | owner principal, dpo |
| `POST /v1/erasure-requests/{id}/reviews` | reviewer, dpo (never the requester or anyone who recorded a manual action on the case) |

### Requester identity verification (upstream)
The framework does **not** verify the Data Principal's identity itself. Requests are expected to
arrive already verified through the deployer's own channel: app or web login, KYC re-check, OTP in
the customer's existing app, contact-centre process, or branch visit. The API records:

- `requested_by`: the authenticated caller (API key name or OIDC identity)
- `verified_by`: the system or person that verified the requester (`self:<identity>` when a principal
  submits through their own authenticated session)
- `verification_ref`: a reference to that verification (session id, KYC check id, case number)

All three appear on the request and in the signed certificate. A principal authenticated through
OIDC can only submit requests for their own `external_id`.

### Durable processing
Verified requests become jobs in the control-plane database. Run `dpdp-rights worker` (ECS service,
Cloud Run job, Kubernetes deployment). Jobs are leased (default 300 s), retried with exponential
backoff, and deduplicated by idempotency key (send an `Idempotency-Key` header on submissions). Keys are
scoped to the caller, stored hashed, and match only an identical request (compared by a keyed digest, so no
personal value is kept for it); reuse for anything else is a 409 that reveals nothing ([details](rights.md#idempotency)).
If a worker dies mid-run, the next attempt skips completed actions, never shreds the vault twice,
and a finished request simply returns its certificate.

### Certificates
Each certificate payload is hashed, chained to the previous certificate, signed
(`certificates.signer`: `aws_kms` with an `ECC_NIST_P256` key, `gcp_kms` with
`EC_SIGN_P256_SHA256`, or `local` Ed25519 for development), and archived
(`certificates.archive`: `s3` with Object Lock COMPLIANCE, `gcs` with a locked retention policy).
Check one with `dpdp-rights verify-certificate --request-id ...` or
`GET /v1/erasure-requests/{id}/certificate/verify`.

### Break-glass access to sealed data
1. A DPO requests a grant with a reason and ticket reference.
2. A different person with the `approver` role approves it (two-person rule).
3. The requester reads specific tokens within the grant window (default 60 min).
Every request, approval, denial and read is written to `access_log` (`GET /v1/break-glass/audit`).

### Tenant isolation
List tenants under `tenants:` in the root config, each pointing to its own config with its own
`lineage.url`, vault storage and KMS keys. The API resolves the tenant from the API key's `tenant`
or the OIDC `tenant` claim. In production, startup fails if two tenants share a database or key.

### Logging and tracing hygiene
- `logging_filter()` tokenises messages inside a DPDP context and **masks** detected PII outside one.
- OpenTelemetry: see [observability.md](observability.md). Spans are tagged with the pseudonymous
  principal and tokenised before export; the collector configs add a redaction processor.

## Production guardrails

`environment: production` blocks startup on: local key wrapper; echo model; SQLite lineage DB;
`api.auth.mode: none`; malformed API key digests; `verification.notifier: log`; unsigned
certificates; regex-only PII detection (unless `pii.allow_regex_only` is set after review); local
sealed key wrapper. It warns on: no separate sealed KEK; vault sharing the lineage DB; local
certificate signer; non-immutable archive; long DEK cache TTL; verification disabled.

## Your responsibilities

- Network: run the API behind a private load balancer / API gateway with TLS, WAF and rate limits.
- Database: PostgreSQL with TLS, encryption at rest, backups, least-privilege users; restrict who can
  read `access_log` and certificates.
- Identity: MFA for DPO and approver accounts; rotate API keys; short JWT lifetimes.
- Deletion windows: database PITR and backups keep wrapped keys for their retention window. Data stays
  unreadable once the live key is gone, but document the window.
- Legal: validate purposes, legal holds, retention periods and the k-anonymity threshold with counsel.
- Pen-test the deployment; this repository has not been independently audited.

## Dependency audit gate

[`scripts/audit_gate.py`](../scripts/audit_gate.py) audits the package **as it is deployed in production**.

**What it covers: the supported production profiles.** `profiles` in
[`.github/audit-policy.yml`](../.github/audit-policy.yml) names each supported deployment shape and its extras:

| Profile | Extras | Pins today |
|---|---|---|
| `aws` | `aws`, `api`, `auth`, `postgres`, `otel`, `redis`, `documents` | 44 |
| `gcp` | `gcp`, `api`, `auth`, `postgres`, `otel`, `redis`, `documents` | 71 |
| `direct-api` | `openai`, `anthropic`, `api`, `auth`, `postgres`, `otel`, `redis`, `documents` | 46 |
| `full` | `all` (every provider and cloud), `documents`, `presidio`, `indic-ner` (transformers, torch and its Linux CUDA libraries), `langchain`, `openai-agents` | 170 |

Each profile is **resolved and audited on its own**, as that deployment would install it. A single-cloud install
can resolve shared dependencies differently from a union of every extra; on 18 November 2026 none did, but
per-profile resolution keeps the audit honest if that changes. `full` is the superset, so every production
extra is resolved at least once; the detector extras add onto any cloud profile. Only `testing` (the
conformance kit's pytest) and `dev` (linters, test doubles, CI tools) are excluded, each with a reason in the
policy. The gate checks `pyproject.toml` on every run: **an extra in no profile and not excluded blocks the
gate**, so a new extra cannot escape the audit unnoticed. To support a new deployment shape, add a profile.

Resolution uses `pip install --dry-run --report`, which reads package metadata only (no torch download), and
the exact pins are audited with `pip-audit --no-deps --disable-pip`. All four profiles take about a minute.

**SBOMs match what was audited.** The release writes each profile's pins and builds one CycloneDX SBOM per
profile from exactly those pins (`cyclonedx-py requirements`, with the package as the root component):
`sbom-aws.cdx.json`, `sbom-gcp.cdx.json`, `sbom-direct-api.cdx.json`, `sbom-full.cdx.json`, each next to its
`audit-pins-<profile>.txt`. The SBOM is never taken from the build environment, so build and audit tools are
not in it. Pick the SBOM for the profile you deploy.

Before anything is attested or published, [`scripts/check_release_artifacts.py`](../scripts/check_release_artifacts.py)
checks that **every profile in the policy** has a non-empty pin file of exact `name==version` lines and a valid
CycloneDX SBOM whose root is this package and whose components are exactly those pins. A missing, empty or
mismatched artifact, or an artifact for a profile the policy no longer defines, stops the release.

**Workflow actions are pinned to full commit SHAs.** Every `uses:` in `.github/workflows/` names a 40-character
commit with the release it corresponds to as a comment (for example
`actions/checkout@11d5960a326750d5838078e36cf38b85af677262  # v4.4.0`), so a moved or replaced tag cannot change
what runs. Dependabot (`github-actions` ecosystem, weekly) proposes updates to these pins; review the upstream
release before merging one. A test fails if any action is left on a tag.

Resolution is for Linux x86-64 with Python 3.12, the reference container. Dependencies that only install on
other platforms are outside the audit; audit your own image if you build for another platform. Optional
models (spaCy, IndicNER weights) are data, not Python packages, and are not audited.

| Where | When | Effect |
|---|---|---|
| Pull requests | every pull request | Advisory: findings are shown in the job summary but do not block unrelated work |
| `main` | every push | Blocking: `main` must pass before a tag is cut |
| Scheduled ([`audit-scheduled.yml`](../.github/workflows/audit-scheduled.yml)) | daily, 03:17 UTC, and on demand | Catches vulnerabilities disclosed after the last change in dependencies that did not change; on failure [`scripts/audit_issue.py`](../scripts/audit_issue.py) opens one tracking issue titled "Scheduled dependency audit failed" (later failures comment on it) |
| Release (`v*` tag) | the built wheel, every profile | **Blocking: no wheel, SBOM or GitHub release is published while the gate fails**; SBOMs per profile from the audited pins |

How it decides:

1. `pip-audit --strict` lists known vulnerabilities in the pinned set. If any package cannot be audited, the
   gate fails.
2. Each finding's severity is looked up in OSV (the GitHub advisory level: low, moderate, high, critical).
   pip-audit does not report severity itself. **A finding with no severity on record counts as critical.**
3. Findings at or above `fail_on` (default **moderate**) block. Lower ones are listed.

**Exception process.** When a finding cannot be fixed before a release (no patched version, or an upgrade is
blocked), add an entry to `exceptions` in the policy file through a pull request reviewed by a maintainer:

```yaml
exceptions:
  - id: GHSA-xxxx-xxxx-xxxx          # as reported by the gate (any alias also matches)
    package: example-package
    reason: Not reachable - we never call the affected parser; upgrade blocked by X
    owner: security@your-org.example
    expires: 2027-01-31              # at most max_exception_days (90) ahead
```

Every field is required. **An exception covers the vulnerability only in the named package**: the same advisory
in another package still blocks, and the summary says which package the exception names. An expired,
incomplete or over-long exception blocks the gate. An exception that no
longer matches a finding is flagged for removal. Accepted findings are shown in every run's summary, so the
risk stays visible. Partners who fork the repository should set their own `fail_on` and approvers.
